## 4. mxai 请求流程

按本机 `mxai` 技能执行 REST API。当前技能文件：`C:/Users/Ferris/.agents/skills/@user_22f85b9d/mxai-cn/SKILL.md`；技能版本 1.4.12。新会话应读取当时安装的技能，不把本文当作永不变化的接口文档。

### 4.1 渠道、配置与模型

- Base URL：`https://mcp.mxai.cn`。这是 mxai 渠道，模型即使叫 GPT 也不能记作本机 image-studio 出图。
- 仅从 `MX_AI_API_KEY` 读取凭据，使用 `Authorization: Bearer` 请求头。密钥不进入项目、提示词、URL、请求记录或工具输出。
- 旧 Codex 进程未继承变量时，在发请求的同一个 PowerShell 中按需载入 Windows User 值；不混用 `OPENAI_API_KEY`。

```powershell
if (-not $env:MX_AI_API_KEY) {
    $env:MX_AI_API_KEY = [Environment]::GetEnvironmentVariable('MX_AI_API_KEY', 'User')
}
# 在同一进程内执行本轮请求脚本；不要输出环境变量值。
```

2026-09-13 本次整理已成功执行 `GET /mcp/api/models?type=image`，真实列表共 12 个模型，包含 `gpt-image-2.5-sunburst`、`gpt-image-2.5-flare`、`gpt-image-2`、`gpt-image-2-origin`、`nano-2.0`、`nano-2.0-pro`。这些相关条目返回 `max_input_images: 1`。静态技能表遗漏了部分 2.5 名称，因此使用**当次真实列表和参数校验**核对；不要猜测别名，也不要静默替换成 `gpt-image-2` 或其他模型。

当前优先 Sunburst，与已采用的 C 图标历史模型一致。Flare 后续已在 A / I1 简化可爱版成功出图，任务号与实际参数见第一阶段记录。下次制作仍核对当次模型与参数。

### 4.2 构建请求与报价

接口：`POST /mcp/api/generate/image`，JSON 使用 UTF-8。`prompt` 必须读取本轮提示词文件的完整内容，不能把文件路径当提示词发出。以下是当前默认参数，仍需在当次调用前校验；Sunburst质量已按用户最新要求由历史 `high` 改为 `medium`：

| 项目 | GPT / Sunburst | Nano 2.0 |
|---|---|---|
| `model` | `gpt-image-2.5-sunburst` | `nano-2.0` |
| `aspect_ratio` | 图标及Furo四格动作表 `1:1`；三视图 `3:2` | 与 GPT 相同 |
| `resolution` | `1K` | `1K` |
| `quality` | `medium`（中） | 省略 |
| `count` | `1` | 省略，历史每请求返回 1 张 |
| `prompt` | 对应完整提示词 | 同风格比较时逐字相同 |
| `input_images` | 按当前任务授权；Furo使用新版全白身体三视图，商店默认纯文生图 | 按当前任务授权 |

可先在相同请求体添加 `dry_run: true` 进行后端参数校验和当前积分报价：不创建任务、不扣积分、不投递队列。正式请求移除该字段或设为 `false`。报价以实时响应为准；历史的 7 积分记录不能当作固定价格。

含参考图的 `dry_run` 只接受已上传 OSS key，不接受 URL 或 base64。不要为了报价擅自上传原图；Furo 已授权输入的同一参考，可按任务需要调用 `POST /mcp/api/upload`，将返回的 `key` 放入 `input_images`。正式生图接口也接受图片 URL 或 base64；本地文件路径本身不是上传内容。

### 4.3 提交、等待与落盘

1. 在新批次目录保存 UTF-8 提示词、物品顺序、模型和不含凭据的参数记录；记录来源渠道、参考图是否获准输入。对比任务核对同风格的提示词哈希一致。
2. 按明确的本轮数量提交。收到真实 `serial_no` 后立即写入任务记录；不要把本地随机 ID 当任务号，不自动重复 POST。
3. 使用 `GET /mcp/api/task/{serial_no}` 轮询，图片约间隔 5 秒。`0` 排队、`1` 生成、`2` 完成、`3` 失败；终态前保持必要进度更新。
4. `status=2` 时，以真实 `image_urls` 保存原始图和脱敏终态记录，下载图片的请求不携带 mxai 认证头。只核对原图可读取、真实尺寸和哈希，随后直接展示原图供用户确认样式；停止图像加工，不能自动进入切分或派生预览。
5. `status=3` 记录并报告 `fail_msg`，不自行重试。提交超时或连接中断时保留现场；有任务号就查该任务，任务状态不明时先核对服务记录，不直接再创建一单。

HTTP 401/403 按技能提示检查 `MX_AI_API_KEY`；5xx、超时和网络失败保留脱敏技术信息。认证头、Cookie、密钥、完整参考图 base64 不得写入项目或错误日志。不能用测试失败时的空文件、旧结果或其他模型输出冒充本次成功。

## 5. 样式确认后的图标切分与透明处理

本节只在用户明确确认相应原图样式并允许继续后执行。“生成一版”“先看看”“做本阶段图片”只授权生成与原图展示，不自动授权本节操作。历史已经加工的试稿保留，不能把历史做法当成今后默认流程。

原画风处理参考：[shop-icons-original-finish.cjs.txt](art/reference/shop-icons-original-finish.cjs.txt)；像素历史版参考：[shop-icons-pixel-finish.cjs.txt](art/reference/shop-icons-pixel-finish.cjs.txt)。以下为已用算法的关键参数，阈值是起点，不是对所有新图都有效的承诺。

1. 读取原图真实宽高、格式和 RGBA 数据，记录字节数与 SHA-256。图标表应为正方形；构图明显错误或数量不符时先记录问题，不强行裁成合格表。
2. **寻找实际空白走廊。** 对 alpha > 0 且 `min(R,G,B) < 220` 的像素按行／列计数；围绕每个四等分位置，在长度约 ±5% 内找宽度至少 4 px 的连续零占用区，选择中心最接近理论格线的一段中点作为切线。
3. 没有安全空白区就报错并复核。历史 GPT 像素表第四行瓶盖超过理论格位，直接等分会切断主体。先逐格原样保存 `source-crops/`，不能先缩成 1K 再掩盖切断问题。
4. **只去除边缘连通的白底。** 从单元格四边做四邻接 flood fill，候选条件为 alpha = 0，或 `min(R,G,B) >= 238` 且 `max(R,G,B)-min(R,G,B) <= 24`；移除像素的 RGBA 清零。保留被闭合轮廓包住的奶白物体和高光，不做全图白色删除。
5. 去底后检查非空、四边没有主体像素。阈值不能替代目视检查：断裂轮廓可能导致白色主体被误吃；纯白区域或阴影也可能误判。出现缺口、残影或白边应局部处理并留下加工说明。
6. 裁到非透明包围盒，最长边等比缩至 184 px，居中放入 256×256 透明画布。**C/D 原画用 Lanczos3；A/B 像素用 nearest。** 最近邻不能把本来顺滑的生成图自动变成正确像素美术；像素语汇首先靠生成质量和验收。
7. 合成标准白底 1K 表、透明 1K 表、深色底预览和比较图；导出 `icons/` 透明单图、`cells/` 白底单元、`manifest.json` 与 `verification.json`。
8. 复核每张实际尺寸、alpha 包围盒、最小留白、切线主体像素、PNG 可解码与哈希；再检查 48／64／128／256 px 下识别性、白边和线宽一致性。交付的是已确认样式的加工结果；若需重新设计造型或另生候选，回到原图确认步骤。

原处理脚本使用了本机 sharp 绝对路径、`__dirname`、历史批次路径，且检测到既有 `manifest.json` 会复用结果。归档的 `.cjs.txt` **是历史参考，不是开箱即用的通用命令**；新批次先复制为独立 `.cjs`，调整输入／输出／依赖路径，改为使用本轮清单，不在旧目录换原图后盲目重跑。像素／原画脚本原本还读取相邻第一轮 `items.json`，新批次应明确使用自己的清单。

B–E 的 C 补盘表为紧密、逐行错位布局，上述固定切线参数不适用。本次以 238 作为占用阈值，扩大搜索范围，允许至少 1 px 的真实空白走廊，列切线逐行求取，并检查每个切块的四边均无主体像素；仅在透明外缘处理白底混色，保留盘面/米饭/玻璃内部白色。具体切线、包围盒、缩放尺寸和哈希见接入清单，不把本次参数盲目用于其他表。

## 7. 人工验收与游戏接入

生成后首先只展示原图样式，用户确认前不开展第 5 节的加工。用户同意继续后，才按获准范围导出透明单图、制作必要的 PNG 深浅底检查，并核对漏画、换位、裁断、白边和白色主体是否被误抠。实际界面验收直接打开开发服务器，不新建 HTML 预览页；已有 compare.html 仅为历史产物，也不代表新一轮已获得后处理授权。

新试稿由用户选方向；用户明确要求替换时，在已授权范围内直接完成，无需再次索要同一确认。仅要求试稿不代表可以批量覆盖运行素材。

接入流程参考 [adopt-c-style.cjs.txt](art/reference/adopt-c-style.cjs.txt)：

1. 修改前查看 `git status --short` 与相关 diff，核对目标清单和 `src/assets.ts` 映射。大批替换前提醒提交留档；保留需要的未跟踪文件，不代提交，不覆盖已有未确认改动。
2. 对获选的透明单图校验来源 manifest / SHA-256；按现有目标尺寸制作所有输出。C 组为 256→128，Lanczos3，RGBA PNG，保留透明留白。先全部准备并校验，再写回。
3. 写入前确认目标文件从读取后没有被其他任务改动；写入后读回哈希。记录源图、修改前后哈希、尺寸、字节数、缩放方式和基线提交，不把基线存在当作覆盖新改动的理由。
4. 按授权启动或复用开发服务器：从项目根执行 `npm.cmd run serve:local`，脚本是 `node scripts/serve-dev.mjs --port 5173`。先确认现有端口服务属于本项目，避免启动冲突；后台启动时使用隐藏窗口。
5. 直接打开开发服务器，检查页面和素材可加载；由用户查看商店、背包、厨房、奖杯柜和小游戏等实际使用处。不用独立 HTML 页面模拟验收。截图／Computer Use 按当前任务授权执行，不能将过去视频任务的操作权限无限沿用。
6. 不改玩家存档来制造验证结果。历史演示使用 `http://localhost:5173/`，与 `http://127.0.0.1:5173/` 的本地存储独立；保留已有真实进度。文档里的历史服务状态不表示新会话时仍在运行。

当前 C 接入记录：16 张 128×128 RGBA PNG，共 262,567 字节，实测最小透明边距 15 px；接入前基线 `ed49129`。来源是 `output/imagegen/shop-icons-20260913-character-style/gpt/icons/`，验证记录是同目录的 `adoption-c-verification.json`。本次文档整理再次核对 16 张运行文件哈希与该记录一致。

只改文档和素材时做相应检查即可，不启动无关发布或打包。新任务若调整映射或业务代码，再运行相关代码检查。
