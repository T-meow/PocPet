# PocPet 1.6.1 发布与验收

## 版本与构建

`package.json` 为版本来源，现为 1.6.1；Tauri、Cargo 和两份锁文件已同步。Node 工具链统一为 24，使用 `npm ci` 安装锁定依赖。`pocpetRelease.fullBuildVersions` 明确将 1.6.1 纳入全量构建，标签发布和产物校验沿用同一规则，其他版本仍遵循原有 x.y.0 自动全量规则。

- `npm run build` 生成普通版 `dist/`；客户端和 Pages 只使用这一版。
- `npm run build:toy` 生成 B 站版 `dist-toy/`，包含 Toy SDK；客户端构建运行会独立上传 `bilibili-web`，不纳入 Release 文件集或 Pages。
- 两个目录均包含 `build-info.json` 和 `asset-manifest.json`。前者记录版本、渠道和 Git 提交，后者用于检查客户端内嵌资源是否陈旧。
- 本地修改尚未提交时，提交编号表示当前 HEAD 基线；发布 CI 只使用对应标签检出的提交。

B 站公告现为“存档提醒”。只禁用宠物改名和新增自定义 Mod 导入，已有自定义 Mod 可继续使用、已有名字暂时保留。图片分享保持开放，宠物卡和年度卡使用当前 Mod 默认名字；普通版分享继续使用玩家设置的名字。

`scripts/check-release.mjs` 检查版本、Git 标签、提交、渠道、资源清单与原生架构，供 CI 和打包脚本复用。`scripts/check-release-assets.mjs` 在全量发布时要求八个文件齐备。

## 自动备份

客户端在应用数据目录的 `backups/` 写入独立的 `pocpet-auto-backup.pocpet`，同时保存最近七个日期的 `daily-YYYY-MM-DD.json`。文件先写入临时文件，再替换目标文件。Windows 默认目录为 `%LOCALAPPDATA%/com.frostforge.pocpet/backups/`。

网页的恢复点保存在 IndexedDB `pocpet-backups`。支持文件授权的浏览器可额外绑定固定文件；权限失效不会中断应用内备份。B 站 App 使用应用内恢复点、文本复制和手动导出，不宣称已将文件保存到下载目录。

主档仍使用 `pocpet.pet.v1`，保护格式与 `schemaVersion: 1` 保持不变。升级前原始内容保存在 `pocpet.pet.v1.pre-upgrade.1.6.1`；每秒保存不再每秒刷新滚动备份。检测其他页面写入后，本页停止持久化并提示重新载入。

## 客户端检查更新

普通版客户端的设置页新增“客户端更新”，默认启动、回到前台及持续前台时检查，每 24 小时最多一次；支持手动检查、明天提醒、忽略版本和关闭自动检查。偏好与缓存独立于宠物存档。网页和 B 站版不显示入口、不请求更新接口。

原生 HTTPS 接口只读取本仓库的正式 Release 和更新清单，10 秒超时；失败不影响游戏或保存。按 Rust 编译的系统、架构匹配安装包，检查版本、普通版标识、文件名、大小和官方链接；打开系统浏览器下载，不自动安装。下载前可直接进入存档页备份。旧 macOS Release 未提供架构时仅显示发布页入口。

发布流程在八种产物检查后生成额外的 `update-info.json`，包含版本、提交和各目标文件信息；macOS 架构从实际构建任务传递。先向草稿 Release 上传完整文件，成功后公开，再部署 Pages。八种交付包的名称保持原样。

存档页按自动备份、导出、导入与恢复分区，统一按钮尺寸、图标和文本框。云存档区域及其提醒开关仅在 B 站云服务可用时显示。

## Android 测试签名与迁移

2026-09-06 使用 `apksigner verify --print-certs` 核对 [GitHub v1.5.0](https://github.com/T-meow/PocPet/releases/tag/v1.5.0) 的 APK，使用 `keytool` 读取本机既有 debug keystore 的公开证书指纹。应用 ID 为 `com.frostforge.pocpet`，旧 `versionCode` 为 10500，1.6.1 为 10601。

| 来源 | SHA-256 |
| --- | --- |
| v1.5.0 arm64 APK | `1651B4C4E45A366D89E03D47F91367C2B29088B2B804B7ACF998F77FEE683C9B` |
| v1.5.0 ARMv7 APK | `FBDBE386A654BD224B7C99EE7A615C31A179F2DDEBCA11021F4242E571656D0D` |
| 本机既有 debug keystore | `E375653D29A6738BC45B1EF34B6B1B6BD86DDA66C53D751DDEE3683ACECCD285` |

三个证书均不相同。用户已确认旧版本仅作测试，未保存原签名。1.6.1 准备采用上述本机现有测试签名，arm64 和 ARMv7 使用同一把固定密钥。旧 GitHub v1.5.0 APK 无法直接覆盖安装新包：必须先导出并确认备份可读，再卸载旧版、安装新版、导入存档。不能在未导出的情况下卸载，否则应用内数据会丢失。之后持续使用同一固定签名，才能覆盖升级；本机此前使用相同测试签名的测试包不受换签影响。

2026-09-07 已获用户授权，并已将本机测试 keystore 配置到仓库 Actions Secrets：`POCPET_ANDROID_ARM64_KEYSTORE_BASE64`、`POCPET_ANDROID_ARMV7_KEYSTORE_BASE64`。采用 debug alias `androiddebugkey` 和 debug 密码。脚本会对照 `scripts/android-signing-reference.json` 的 1.6.1 固定指纹，缺失或不匹配即失败；该文件另行保留旧签名指纹用于迁移说明。不要把 keystore 或编码内容提交到仓库，也不要重新生成或随意替换这把固定密钥。

本机未启用符号链接权限，Tauri Android 完整构建会在编译原生库后停止。显式本地命令 `npm run package:android:arm64:reuse` / `npm run package:android:armv7:reuse` 可复用已编译的库，但必须通过当前前端资源和架构检查。CI 禁用此分支；任何 Tauri 失败都会终止任务。

## 发布流程

PR 和分支提交只执行版本校验、关键存档检查和双版本构建。`workflow_dispatch` 手动运行始终只构建，即使选择标签也不会发布。正式 `v*` 标签的 push 才会生成客户端并发布 Release，所有必需平台成功后再调用 Pages 工作流。

Pages 直接下载同一次运行中验证过的 `standard-web`，检查版本、提交和普通版标识，不重新构建或读取最新 main。每次正式版本都产生 Pages 部署产物；Web zip 仅随全量发布生成。部署失败可以重试原运行的失败任务，继续使用原产物。

发布前还需经明确指令完成以下远端操作：

1. 两个固定测试签名 Secrets 已配置；恢复构建后核对 APK 实际签名，并保留旧版用户先备份再重装的迁移说明。
2. 在 `Settings > Environments > github-pages` 的部署规则中允许 `v*` 标签；原规则只有 main，不修改会阻塞标签部署。
3. 保持仓库 Pages 地址 `https://t-meow.github.io/PocPet/`、应用 ID 和原有数据归属不变。
4. 提交后先手动运行全量 CI，确认 Windows x64/x86、Android arm64/ARMv7、Web zip、macOS dmg、Linux AppImage/deb 八种产物。
5. 完成真机覆盖升级与备份验收后，按后续指令推送正式标签。
